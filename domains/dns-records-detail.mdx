DNS records tell the internet how to resolve your domain name — where to send website visitors, which server handles your email, and how to verify ownership or authenticate your messages. This page explains the record types you will work with in the [EDIS PowerDNS-Admin portal](https://pdns.edis.global/login), along with special notation like `@` and `*`, and how quickly changes propagate for `.at` domains.

## Special Name Notation

Before looking at individual record types, it helps to understand two special values you will see in the **Name** column of the zone editor:

- **`@`** — Refers to the root domain itself (e.g., `example.at`). Use `@` when you want a record to apply to the bare domain rather than a subdomain.
- **`*`** (wildcard) — Matches any subdomain that does not have an explicit record. For example, `*.example.at` would respond for `shop.example.at`, `blog.example.at`, and so on — unless those subdomains have their own dedicated records, which take precedence. A wildcard does not override existing records and does not extend to TLS certificates automatically; verify that your hosting and certificate configuration actually covers the hostnames the wildcard resolves to.

## Record Types

<AccordionGroup>
  <Accordion title="A Record — IPv4 Address">
    An **A record** maps a hostname to an **IPv4 address**. It is the most common record type for pointing a domain or subdomain to a web server.

    When a visitor types your domain name into a browser, their device sends a DNS query that ultimately resolves the domain to an IPv4 address via the A record. The server at that address then delivers your website content.

    **Data field:** Enter only an IPv4 address (e.g., `185.201.9.10`). Do not enter a hostname, URL, or any `http://` prefix — those are invalid values for an A record.

    **Example:**

    | Name | Type | Data |
    |---|---|---|
    | `@` | A | `185.201.9.10` |
    | `www` | A | `185.201.9.10` |

    <Note>
      If you also have an AAAA record (IPv6) for the same hostname, both records must point to servers that deliver the correct content and hold a matching TLS certificate. When migrating to a new provider, check both the A **and** AAAA records — leaving a stale AAAA record pointing at the old server can cause intermittent connectivity issues for IPv6-capable visitors.
    </Note>
  </Accordion>

  <Accordion title="AAAA Record — IPv6 Address">
    A **AAAA record** (pronounced "quad-A") maps a hostname to an **IPv6 address**. It works identically to an A record, except the data field holds an IPv6 address rather than an IPv4 address. The name "quad-A" reflects that an IPv6 address is four times the length of an IPv4 address.

    IPv6 connectivity is increasingly common, and EDIS hosting configurations typically include AAAA records by default. If you change your A record during a server migration, check whether a corresponding AAAA record exists and update or remove it as needed.

    **Data field:** Enter only an IPv6 address (e.g., `2a02:418:6a04::10`). Do not enter a hostname or URL.

    **Example:**

    | Name | Type | Data |
    |---|---|---|
    | `@` | AAAA | `2a02:418:6a04::10` |
    | `www` | AAAA | `2a02:418:6a04::10` |

    <Warning>
      After changing an A record, always verify your AAAA record too. A mismatched AAAA entry — one that still points to the old server — will cause your site to be unreachable for visitors whose devices prefer IPv6.
    </Warning>
  </Accordion>

  <Accordion title="CNAME Record — Alias / Canonical Name">
    A **CNAME record** creates an alias from one hostname to another. Instead of resolving to an IP address directly, a CNAME points to a different hostname (the canonical name), and the DNS system then resolves that target hostname to its IP address. This means that if the target's IP address changes, the CNAME automatically follows — no update to the alias record is needed.

    **Data field:** Enter a fully qualified hostname (e.g., `mysite.example.com.`). Do not enter an IP address or a URL with `http://`.

    **Example:**

    | Name | Type | Data |
    |---|---|---|
    | `www` | CNAME | `mysite.beiEdis.at.` |
    | `shop` | CNAME | `store.provider.com.` |

    <Warning>
      A CNAME must **never** be set for the root domain (`@`). According to DNS specifications, a CNAME cannot coexist with other record types at the same name, and the root domain always requires NS and SOA records — making a CNAME at `@` invalid. Use an A or AAAA record for the root domain instead.
    </Warning>
  </Accordion>

  <Accordion title="MX Record — Mail Server">
    An **MX record** (Mail Exchanger) tells the internet which mail server is responsible for accepting email for your domain. When someone sends an email to `you@example.at`, their mail server looks up the MX record for `example.at` to find out where to deliver the message.

    MX records include a **priority** value (lower number = higher priority). If you have multiple MX records, mail delivery is attempted at the lowest-priority-number server first; the others serve as fallbacks.

    **Data field:** Enter a fully qualified hostname of a mail server (e.g., `mx.edis.at.`). Do not enter an IP address.

    **Example for EDIS mail hosting:**

    | Name | Type | Priority | Data |
    |---|---|---|---|
    | `@` | MX | `10` | `mx.edis.at.` |

    <Note>
      The EDIS mail server hostname is **mx.edis.at**. Use this value for the MX record when your email is hosted at EDIS.
    </Note>
  </Accordion>

  <Accordion title="TXT Record — Text / SPF / Verification">
    A **TXT record** holds arbitrary text data. While originally intended for human-readable notes, TXT records are now widely used for machine-readable values including:

    - **SPF (Sender Policy Framework)** — specifies which mail servers are authorised to send email on behalf of your domain
    - **Domain ownership verification** — used by services like Google Search Console, Microsoft 365, and others
    - **DKIM public keys** — used to verify email signatures
    - **DMARC policies** — defines how receivers should handle unauthenticated email

    **Data field:** Enter the text value **without surrounding quotation marks or apostrophes**. The portal adds the required quotes automatically when publishing the record.

    **Correct:**
    ```
    v=spf1 a:spf.edis.at -all
    ```

    **Incorrect:**
    ```
    "v=spf1 a:spf.edis.at -all"
    ```

    <Warning>
      Your domain must have **exactly one SPF TXT record**. If multiple servers are authorised to send email for your domain, combine them into a single SPF record rather than creating multiple separate TXT records. Multiple SPF records cause SPF evaluation to fail.
    </Warning>

    **Example:**

    | Name | Type | Data |
    |---|---|---|
    | `@` | TXT | `v=spf1 a:spf.edis.at -all` |
    | `_dmarc` | TXT | `v=DMARC1; p=none; rua=mailto:dmarc@example.at` |
  </Accordion>
</AccordionGroup>

## Propagation Times for .at Domains

When you change DNS records within your zone (A, AAAA, MX, TXT, etc.) and the nameservers remain the same, the change is published immediately to the EDIS Anycast nameservers once you click **Apply Changes**. How quickly the change is visible worldwide depends on the TTL of the record and how long resolvers have cached the old value.

When you change the **nameserver delegation** of a `.at` domain (i.e., you update which nameservers are authoritative), the change must be processed by the `.at` zone registry (nic.at). The EDIS domain FAQ documents that the `.at` zone refreshes at the top of each hour.

<Note>
  An hourly `.at` zone refresh does not mean your nameserver change will be globally visible within 60 minutes. There are separate steps involved: the registrar submitting the request, the registry publishing the delegation, and resolvers worldwide expiring their cached NS records. Check the confirmed order status and the remaining TTL on the old NS records to estimate actual propagation.
</Note>

After making any DNS change, verify it by querying the authoritative nameservers directly (e.g., `dig @ns1.edis.global example.at A`) rather than relying on a resolver that may be returning a cached answer. Do not make additional changes just because one resolver still shows the old value — wait for the TTL to expire.
