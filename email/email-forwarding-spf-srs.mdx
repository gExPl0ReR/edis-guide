Email forwarding is a convenient feature — messages sent to one address are automatically redirected to another. However, forwarding can interact in unexpected ways with SPF (Sender Policy Framework) records, especially when strict SPF policies (`-all`) are in place. Understanding how this works helps you avoid delivery failures and configure your setup correctly.

## How SPF works (briefly)

SPF checks whether the mail server that is actually delivering a message is authorised to send on behalf of the domain in the envelope sender address (the technical `MAIL FROM` address, which is different from the visible `From:` header). The sending domain publishes a list of authorised IP addresses in a DNS TXT record, and the receiving server checks whether the delivering server's IP is on that list.

## Why forwarding breaks SPF

When a forwarding rule redirects a message, the forwarding server connects to the final destination server and delivers the email. If the forwarding server keeps the original envelope sender address intact, the final recipient's server will check SPF against the **original sender's domain** — but the IP address making the connection belongs to the **forwarding server**, not the original sender.

Unless the forwarding server's IP is listed in the original sender's SPF record (which it typically is not and should not be), the SPF check fails.

```
Original flow:
  sender@external.com → [external mail server] → recipient@yourdomain.com

With forwarding to another address:
  sender@external.com → [external mail server] → [EDIS forwarder] → final@destination.com
                                                         ↑
                                        SPF checks external.com's record
                                        against the EDIS forwarder IP — FAIL
```

This failure can cause the final destination server to reject or spam-flag the forwarded message, even though the original email was completely legitimate.

## How SRS solves the problem

SRS (Sender Rewrite Scheme) is a technique used by forwarding servers to rewrite the technical envelope sender address so that SPF checks pass at the final destination.

When SRS is active, the EDIS forwarding server rewrites the `MAIL FROM` address to one that belongs to the EDIS domain (e.g. `SRS0=hash=tt=external.com=sender@edis-domain.com`). The SPF check at the destination server now evaluates whether the EDIS forwarder is authorised to send for the EDIS domain — which it is.

```
With SRS:
  sender@external.com → [external mail server] → [EDIS forwarder with SRS]
                                                       ↓
                                Envelope sender rewritten to EDIS SRS address
                                       ↓
                               final@destination.com
                               SPF checks EDIS domain — PASS
```

<Note>
  SRS rewrites only the technical envelope sender (`MAIL FROM`), not the visible `From:` header. The recipient still sees the original sender's name and email address in their inbox. SRS does not affect DKIM signatures on the original message either (unless the message body is modified in transit, which would break the signature regardless).
</Note>

## Enabling SRS at EDIS

EDIS supports SRS for email forwarding rules configured in the vHost panel. When you set up a forwarding address, SRS is applied to outbound forwarded messages to prevent SPF failures at the destination.

To configure a forwarding address in the vHost panel, see [Set Up Email Mailboxes and Forwarding](/email/mailbox-setup).

<Note>
  If you are experiencing delivery failures with forwarded messages, check that the forwarding address is configured as a proper **forwarding rule** in the EDIS vHost panel, not as a client-side redirect. Server-side forwarding through the vHost panel benefits from SRS rewriting; manually re-sending from an email client does not.
</Note>

## DMARC and forwarding

SRS addresses the SPF problem, but DMARC introduces an additional requirement: **alignment**. DMARC requires that either the SPF-validated domain or the DKIM-validated domain matches the visible `From:` domain.

With SRS, the SPF now passes for the EDIS domain, but the EDIS domain does not match the original sender's `From:` domain. This means **SPF alignment for DMARC may still fail** for forwarded messages.

If the original message carries a valid DKIM signature that has not been broken in transit, DKIM alignment can satisfy DMARC instead. Whether forwarded messages pass DMARC depends on:

- Whether the original sender signs with DKIM
- Whether the forwarding process modifies the message body or headers (which would break the DKIM signature)
- The DMARC policy of the original sender's domain

## Diagnosing forwarding failures

If a forwarded message is rejected, the bounce notification typically includes a reason such as `550 rejecting for sender policy framework`. To investigate, you need:

- The **full bounce-back text**
- The **original sender's address** and domain
- The **forwarding address** configured at EDIS
- The **final destination address**
- The date and time of the failure

Do not modify the SPF record of the destination domain to include the forwarding server — that is not the correct solution and could affect other mail flows. Instead, verify that SRS is in effect for your forwarding rule and test again with a fresh message.

Contact [hosting@edis.at](mailto:hosting@edis.at) if the issue persists after verifying your forwarding configuration.
