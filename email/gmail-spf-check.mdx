If you send an email to a Gmail address and receive a bounce-back, there is a good chance it relates to email authentication. Gmail enforces strict sender authentication requirements and will reject or flag messages that fail SPF, DKIM, or DMARC checks. This guide walks you through how to identify the problem and fix it.

## Recognising the error

A typical Gmail rejection looks like this in your bounce notification:

```
550-5.7.1 This message does not have authentication information or fails to
550-5.7.1 pass authentication checks. To best protect our users from spam,
550-5.7.1 the message has been blocked. Please visit
550-5.7.1 https://support.google.com/mail/answer/81126#authentication
```

This message tells you that the email either had no authentication at all, or that the authentication checks (SPF, DKIM, DMARC) failed. The steps below help you determine which is the case.

<Steps>

### Check whether your domain has an SPF record

Look up the TXT records for your domain using a tool such as [MX Toolbox SPF Lookup](https://mxtoolbox.com/spf.aspx) or by running:

```bash
dig TXT yourdomain.com
```

Check for a line that contains `v=spf1`. If no such record exists, you need to add one. See [Set Up an SPF Record](/email/spf-record) for the full guide.

### Verify there is exactly one SPF record

Search the results carefully. If you see **two or more TXT records** for the same hostname that both begin with `v=spf1`, this is a permanent SPF error (`permerror`). Gmail and other providers will treat this as a failed authentication.

<Warning>
  You must have **only one** SPF TXT record per hostname. If you have duplicates, delete the outdated one and merge all authorised senders into a single record. Do not simply add a new record — edit the existing one.
</Warning>

### Confirm the EDIS SPF mechanism is present

If an SPF record exists, check that it includes the EDIS sending infrastructure. For domains that send through EDIS, the record should contain `a:spf.edis.at`:

```dns
@ TXT "v=spf1 a:spf.edis.at -all"
```

If you also send through other services (for example Google Workspace, Mailchimp, or a CRM), those must be included in the same record.

### Verify you are sending through the correct mail server

The SPF check is based on the server that actually sends the message — the SMTP relay — not the `From:` address visible in the email client. If you are sending through `mailrelay.edis.at` with SMTP authentication, the EDIS SPF record covers this. If you are sending through a third-party service, that service's IP addresses must be included in your SPF record.

### Test with a new send after the fix

DNS changes can take up to a few hours to propagate fully. After updating your SPF record, wait at least 15–30 minutes, then send a fresh test message to a Gmail address. Check the Gmail message headers (open the message → three-dot menu → **Show original**) for the SPF and DKIM result lines.

<Note>
  In Gmail's "Show original" view, look for lines like `Authentication-Results` that contain `spf=pass` or `spf=fail`. A passing SPF check confirms your record is correctly configured.
</Note>

### Review DKIM if SPF alone does not resolve the rejection

If SPF is passing but Gmail is still rejecting messages, check whether DKIM signing is configured for your domain. DKIM provides a cryptographic signature that further verifies the message came from an authorised source. Contact [hosting@edis.at](mailto:hosting@edis.at) to confirm whether DKIM is available for your specific hosting configuration.

</Steps>

## What to include when contacting support

If you have followed these steps and mail is still being rejected, contact EDIS support at [hosting@edis.at](mailto:hosting@edis.at). Include:

- The **full bounce-back message** (not just the subject line)
- The domain you are sending from
- The sending service or SMTP relay you are using
- The date and time of the rejected message (with time zone)
- The result of your SPF record lookup

Do not include passwords or private credentials in your support request.
