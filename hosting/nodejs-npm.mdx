EDIS shared hosting allows you to install Node.js and npm under your own user account via SSH. This is useful for running build tools (such as Webpack, Vite, or Sass compilers) or executing Node.js scripts as part of your workflow. Because Node.js is installed in your home directory rather than system-wide, you manage versions yourself and the installation does not affect other accounts on the server.

<Note>
SSH access is available on **Ristretto** hosting plans and higher. You can find your SSH credentials in the vHost panel at [https://manage.edis.at/vhost/](https://manage.edis.at/vhost/) under the SSH section.
</Note>

<Warning>
Installing Node.js and npm in your own account does **not** provide managed Node.js hosting with persistent background processes. Running a permanently available Node.js web server requires process management tools (such as PM2), dedicated ports, and possibly a reverse proxy — these capabilities are not part of standard shared hosting. If your application needs to run as a persistent service, contact [hosting@edis.at](mailto:hosting@edis.at) to discuss your requirements before starting the setup.
</Warning>

## Install Node.js via SSH

<Steps>
  <Step title="Connect to your webhost via SSH">
    Open a terminal and connect using your vHost key and the EDIS SSH gateway:

    ```bash
    ssh ssh.at.edis.global -l VHOSTKEY -p 22
    ```

    Replace `VHOSTKEY` with your actual vHost access key, which you can find in the vHost panel.
  </Step>
  <Step title="Create a directory for Node.js">
    Navigate to your `www` directory and create a dedicated folder for the Node.js installation:

    ```bash
    cd www/
    mkdir nodejs
    cd nodejs
    ```

    Keeping Node.js in its own directory makes it easier to update or remove later.
  </Step>
  <Step title="Download a Node.js release">
    Visit [https://nodejs.org/en/download](https://nodejs.org/en/download) to find a current LTS release. Choose the **Linux x64** binary tarball. Then download it directly to your server — replace `vxx.x.x` and the filename with the actual version you chose:

    ```bash
    wget https://nodejs.org/dist/vxx.x.x/node-vxx.x.x-linux-x64.tar.gz
    ```

    After downloading, verify the checksum against the SHA256 values published on the Node.js website before proceeding.
  </Step>
  <Step title="Extract the archive">
    Unpack the downloaded tarball:

    ```bash
    tar -xzf node-vxx.x.x-linux-x64.tar.gz
    ```

    This creates a directory named `node-vxx.x.x-linux-x64/` containing the Node.js binaries.
  </Step>
  <Step title="Add Node.js to your PATH">
    Change into the `bin` directory of the extracted release and note the full path:

    ```bash
    cd node-vxx.x.x-linux-x64/bin
    pwd
    ```

    The `pwd` command outputs the full path, for example:
    ```
    /home/VHOSTKEY/www/nodejs/node-v20.9.0-linux-x64/bin
    ```

    Add this directory to your shell's search path for the current session:

    ```bash
    export PATH="$(pwd):$PATH"
    ```

    To make this permanent across future SSH sessions, add the same `export PATH=...` line (using the full absolute path, not `$(pwd)`) to your shell configuration file — typically `~/.bashrc` or `~/.bash_profile`.
  </Step>
  <Step title="Verify the installation">
    Confirm that `node` and `npm` are found and report the expected versions:

    ```bash
    node -v
    ```
    Example output: `v20.9.0`

    ```bash
    npm -v
    ```
    Example output: `10.1.0`

    If the commands are not found, double-check that the `export PATH` step was executed correctly in the current session and that you are in the right shell.
  </Step>
</Steps>

## Check Which Binary Is Being Called

After setting up the PATH, verify that the shell resolves `node` and `npm` to your newly installed binaries rather than any system-level versions:

```bash
command -v node
command -v npm
```

Both commands should return paths pointing to your installation directory, for example:
```
/home/VHOSTKEY/www/nodejs/node-v20.9.0-linux-x64/bin/node
/home/VHOSTKEY/www/nodejs/node-v20.9.0-linux-x64/bin/npm
```

## Build Tools vs. Persistent Services

Understanding the difference between these two use cases helps you avoid surprises:

<CardGroup cols={2}>
  <Card title="Build Tools" icon="hammer">
    Tools like Webpack, Vite, Parcel, or Sass run a process that generates output files and then exits. This is fully supported in EDIS shared hosting — you run the build command, it completes, and the resulting static files are served by Apache.
  </Card>
  <Card title="Persistent Services" icon="server">
    A Node.js HTTP server (e.g. Express) needs to run continuously, listen on a port, and be restarted if it crashes. This requires PM2 or a similar process manager, open ports, and possibly a reverse proxy — capabilities that go beyond standard shared hosting.
  </Card>
</CardGroup>

<Tip>
If you only need to compile assets or run one-off scripts, standard shared hosting is sufficient. If you need a permanently running Node.js application, contact EDIS support to discuss a suitable hosting solution before beginning your setup.
</Tip>

## Resource Considerations

Node.js builds can be memory- and CPU-intensive. Keep in mind:

- Your hosting plan has a fixed resource budget (RAM, CPU). Large builds may be slow or may be terminated if they exceed the plan's limits.
- Installed `node_modules` directories can become very large. Monitor your disk quota regularly with `du -sh ~/www/nodejs/` or similar.
- Use `.npmrc` or the `--prefix` flag to control where global npm packages are installed so they stay within your user directory.

For questions about plan limits or suitability for your use case, reach out to [hosting@edis.at](mailto:hosting@edis.at).
