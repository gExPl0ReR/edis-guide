After a DNS change or server migration, your domain may become unreachable for some visitors even though you updated the A record. In many cases the cause is an **outdated or incorrect AAAA record** (IPv6 address). By default, EDIS configures both A and AAAA records for hosted domains, so when you change the IPv4 address you must also update the IPv6 address — otherwise visitors whose devices prefer IPv6 will be sent to the wrong server.

## How the Mismatch Causes Downtime

Modern operating systems and browsers prefer IPv6 over IPv4 when both are available. If your AAAA record still points to an old or incorrect server after a migration, IPv6-capable visitors will reach the old server (which may no longer serve your site) while IPv4-only visitors reach the new server correctly. This creates an inconsistent experience: the site works for some people and not for others, which can be difficult to diagnose.

<Tip>
  After any server migration or IP address change, always check **both** your A record (IPv4) and your AAAA record (IPv6). Updating only one of the two is the most common cause of intermittent post-migration outages.
</Tip>

## Checking and Fixing Your DNS Records

<Steps>
  <Step title="Identify Your Current A and AAAA Records">
    Log in to the [EDIS DNS portal](https://pdns.edis.global/login) and open the DNS zone for the affected domain. Note the current values for both the **A record** (IPv4) and the **AAAA record** (IPv6).
  </Step>

  <Step title="Compare Against Your Server's Actual IP Addresses">
    Confirm the correct IPv4 and IPv6 addresses for your server. You can find these in your EDIS hosting control panel or in the server provisioning email. Compare them with what is in the DNS zone.
  </Step>

  <Step title="Update Any Incorrect Records">
    Edit the A record and the AAAA record so that both point to the correct addresses for your current server. If your server does not have an IPv6 address, remove the AAAA record entirely rather than leaving an outdated value in place.
  </Step>

  <Step title="Check Consistency Across Subdomains">
    Repeat the same check for any subdomains (such as `www`) that have separate A or AAAA records. A mismatch on a subdomain record causes the same problem for URLs that use that subdomain.
  </Step>

  <Step title="Wait for Propagation and Verify">
    DNS changes at EDIS are published promptly, but cached answers at third-party resolvers persist until the TTL expires. Verify the new records using an authoritative query tool and then test access from a real network connection.

    <Note>
      If the site is still unreachable from a specific network after DNS has propagated, the issue may be a network-level block rather than a DNS problem. Try accessing the domain from a different internet connection to rule this out.
    </Note>
  </Step>
</Steps>

## Testing from a Specific Network

If the domain is unreachable only from one particular network (for example, a school or corporate connection), record the exact URL, the time, the error message, and the public IP address of the affected connection. Many devices in a shared network use the same public IP, so a block on that address affects all of them simultaneously. Contact EDIS support with those details so the correct IP or network range can be reviewed and any accidental block can be lifted.
